# 审校记录 · 第 23 课 · MoE 训练

- **date**: 2026-11-26
- **lesson**: 第 23 课 · MoE 训练：专家并行怎么排、路由为什么抖、dropless 付什么账
- **verdict**: revise

## summary

整体是一份结构较完整、算术基本正确的讲义：第 1–6 步的 KiB/MiB/GiB 换算和 9%/75% 都对；第 7 步的算术（1.41 GFLOP→1.44 TFLOP→3.6 ms）也对，但推导把“本卡 token”与“本卡处理的 token”混为一谈。主要问题集中在三处概念表述：第 7 步推导、四跳计数、grouped GEMM 的“最忙专家”；另有 z-loss“只改数值不改分配”与“防饱和”矛盾、“训练侧不能重排”过于绝对、两条推测写成事实，以及缺课后自测和 all-reduce/routed 专家/亲和分数等术语。小问题：V3 最后 500B 是置 γ=0 而非退火；“跨节点流量无上界”应为上界 min(k,节点数)=8；“卡内”应为“超节点内”；400 GB/s 未说明单向/双向；fᵢ max/mean>3 无来源；容量公式 ⌈T·k/N·C⌉ 缺括号；教学配置每卡专家权重约 86 GB，32 卡不可部署；“9% 藏得住”需说明靠 micro-batch 重叠；0.006 是 V3 的参考初始化 std，不是“过大”的例子。

## issues

### 1. [high]

- **claim**: 第 7 步：每卡 1024 token→1.44 TFLOP
- **问题**: 本卡只驻留 4/128 个专家；对本卡 1024 个本地 token，平均只算 1024×4×(4/128)=128 个专家-token 对（≈0.045 TFLOP），不是 1.44 TFLOP。1.44 TFLOP 来自本卡处理全部 32 张卡送来的 token（均衡时 32×1024×4/32=4096 对）。原文把“本卡 token”与“本卡处理的 token”混为一谈，数字碰巧对，推导错了；初学者会以为一张卡要算本地 token 的全部 4 个专家。
- **建议**: 改成“均衡时每卡共处理 4096 个专家-token 对，4096×2×176M≈1.44 TFLOP/层”，并说明本卡也算别的卡送来的 token。

### 2. [high]

- **claim**: 前向四步、反向两跳，所以每层每步是 4 次 all-to-all
- **问题**: 前向四步（重排、dispatch、grouped GEMM、combine）里只有 dispatch 和 combine 是 all-to-all；4 次 = 前向 2 次 + 反向 2 次（combine 的转置、dispatch 的转置）。原文的“所以”不成立，初学者会数成 6 次，或把重排/GEMM 当成 all-to-all。
- **建议**: 改为“前向两跳（dispatch、combine）＋反向两跳（combine^T、dispatch^T）＝每层每步 4 次 all-to-all”。

### 3. [high]

- **claim**: grouped GEMM：各专家 token 数不同、拼不成一个矩阵乘，时长由最忙的专家定
- **问题**: 拼不成一个 GEMM 的主因是各专家权重不同，token 数不同只是让形状可变；而单卡 grouped GEMM 的时长≈本卡各专家工作量之和，不是 max。“最忙的专家”只决定缓冲/padding；跨卡 straggler 看“最忙的卡”（4 个专家总负载最大）。原文把“最忙专家”和“最忙卡”混了。
- **建议**: 改为：各专家权重不同，需 grouped/batched GEMM；单卡内按总工作量估时，卡间按最忙的卡估 straggler；只有按 max 段 padding 的实现才由最忙专家定。

### 4. [medium]

- **claim**: z-loss：只改数值不改分配
- **问题**: z-loss 惩罚 log-sum-exp，会直接改变 logits 尺度和 softmax 分布，从而改变路由；它只是不直接以负载均衡为目标。原文“只改数值不改分配”与同表“防饱和”自相矛盾。
- **建议**: 改为“不直接优化负载均衡，但会改变 logits 尺度、间接影响分配；防饱和本身就是改分配”。

### 5. [medium]

- **claim**: 重排推理侧能做、训练侧不能，因为训练权重每步都在变
- **问题**: 训练侧并非绝对不能重排；可以在 checkpoint 边界搬专家/优化器状态，只是代价高、会打断流水与图捕获，通常不做或低频做。“权重每步都在变”不是根本障碍（推理权重也会变，只是不训练）。
- **建议**: 改为“训练侧重排代价高（搬权重与优化器状态、打断流水），一般不做或只在 checkpoint 边界做；推理侧可以频繁做”。

### 6. [medium]

- **claim**: 数据重复让表示聚团、router 无区分度；被 drop 的恰是热门方向的高频模式
- **问题**: 这两条都是把推测性的因果链写成事实：数据重复→表示聚团→router 无区分度没有给出证据；被 drop 的 token 是“路由到过载专家”的 token，不等于“热门方向的高频模式”，也可能只是顺序靠后/长度分布导致。用“恰是”过于绝对。
- **建议**: 改为“可能/常见于”，并给出排查方法；把“被 drop 的是高频模式”改成“被 drop 的 token 与路由分布相关，故梯度有偏”，注明这是机制解释而非已证结论。

### 7. [medium]

- **claim**: 教学结构：有课前自测，但没有课后自测题
- **问题**: 结构有课前自测、核心概念、例子、误区、术语卡、来源，但没有课后自测题，无法检验学习效果，也与“课前自测”不对称。第 1 题“一卡这一步算几份专家输出”还有歧义（每 token、每 step、还是驻留数）。
- **建议**: 加 3–5 道课后自测（含答案），覆盖四跳计数、容量公式、dropless 代价、M 的作用、路由三病；把第 1 题改成“每卡驻留几个专家？每个 token 最多在本卡算几份？”

### 8. [medium]

- **claim**: 术语卡：未收 all-reduce、routed 专家、亲和分数
- **问题**: all-reduce 在课前自测和第一节就用了，术语卡只收 all-to-all；routed 专家（相对 shared 专家）在 V3 例子中出现但没解释；亲和分数/affinity 在节点受限路由里直接使用。基础弱的工程师会卡住。
- **建议**: 术语卡补 all-reduce、routed/shared expert、affinity score；正文首次出现时各给一句定义。
