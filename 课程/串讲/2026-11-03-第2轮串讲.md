# 第 2 轮串讲 · 2026-11-03

> 本轮四课：第 5 课 · 推理服务基础：prefill/decode 与 KV cache、第 6 课 · vLLM 引擎架构、第 7 课 · 昇腾 NPU 架构与 CANN 生态（上）、第 8 课 · 昇腾 NPU 架构与 CANN 生态（下）

## 一张图串起来

四课是同一个问题的四层：一个 token 怎么又快又便宜地出来。

```text
请求→API Server(分词)→Engine Core(token 预算+KV 块表)→NPU Worker
                          ↑______ 每 token 回调度器 ______│
空间账：KV 池=显存−权重−激活      时间账：prefill 计算受限／decode 带宽受限
CANN(AscendCL/算子库) → 驱动/固件 → AI Core(Cube 16³) + HBM
```

因果链这样读：decode 带宽受限（读 14 GB 权重 8.75 ms，算术强度 1 FLOP/字节，平衡点约 188），单请求仅 114 token/s，只能加 batch——8 个请求共用一次读取，吞吐 ×8、延迟不变。可 batch 上限是 KV 显存（每 token 约 512 KB，2048 token 就吃 1 GB，一个 100+200 token 的请求也要 150 MB），于是 PagedAttention 按 16 token 分块省显存；省下来才敢按 token 预算随进随出、长 prompt 切块混批，prefill 吃算力、decode 吃带宽，正好互相填坑。算子落到 AI Core 靠 CANN，融合少写回一次 HBM 就是还回带宽。一句话：**第 5 课定指标，第 6 课把这些指标做成可调的旋钮，第 7、8 课解释旋钮为什么有上限。**

## 综合自测

### 1. decode 的 batch 从 1 加到 8，为何吞吐约 ×8 而单请求延迟不变？
<details><summary>查看答案</summary>8.75 ms 的权重读取是固定成本：batch=1 只服务 1 个 token（114 token/s），batch=8 时同一遍读取服务 8 个（914 token/s），每人分到的延迟没变。对应 `--max-num-seqs`。但两头封顶：KV 爆了会抢占重算，batch 够大后翻转为计算受限、吞吐趋平——结论只在带宽受限区间成立。</details>

### 2. 64 GB 的 910B 跑 7B FP16、显存配额 0.9，KV 池多大、能装几个 2048 token 请求？为何别开到 1.0？
<details><summary>查看答案</summary>配额约 57.6 GB，减权重 14 GB，KV 池约 43 GB（再扣激活更小）；每请求 512 KB×2048≈1 GB，约 40 个并发，是粗算上界。开到 1.0 会挤掉系统缓冲、有 OOM 风险：权重、激活、KV、通信缓冲共用这份配额；且并发还被算力与 `--max-model-len` 约束。</details>

### 3. 用户 A 说「首字 3 秒才出来」，B 说「每个字都慢」，各查哪个指标？
<details><summary>查看答案</summary>A 是 TTFT，落在 prefill 与排队：查 prompt 是否过长、是否排长队、prefix caching 是否命中（长系统提示词没命中就每请求重算）。B 是 TPOT，落在 decode 单步：查同批请求数是否过大、带宽是否打满。用 profiler 验：利用率高=算力瓶颈（偏 A），利用率低但拷贝多=带宽瓶颈（偏 B）。</details>

### 4. 100 个请求共享 1000 token 系统提示词，prefix caching 省多少？若各自生成 2000 token 还值得开？
<details><summary>查看答案</summary>省约 99 次 prefill：2·N·P≈2×7×10⁹×1000≈1.4×10¹³ FLOP/次，99 次约 1.4×10¹⁵，按 100 TFLOPS 估算约 14 秒。但它只省 prefill 与 KV 内存，不省 decode，每个请求仍要串行生成 2000 token。仍值得开（零成本），只是收益随共享前缀占比上升、随输出长度下降。</details>

### 5. chunked prefill 为什么能提升整卡效率？它化解了哪两课的两个瓶颈？
<details><summary>查看答案</summary>它把长 prompt 切块与 decode 同批提交。按第 7 课判据：prefill 的 M 大、计算受限（Cube 忙带宽闲），decode 的 M=1、带宽受限（带宽忙 Cube 闲），混批让两条流水线互相填坑。同时解决第 5 课「长请求卡住整批」：长 prompt 不再独占设备，短请求的 TTFT 不被拖死。</details>

### 6. 一次 `torch.mm` 从 Python 到 AI Core 穿过哪几层？报 `CANN not found` 按什么顺序查？
<details><summary>查看答案</summary>`torch.mm`→torch-npu（注册 npu 设备、映射算子）→AscendCL（设备、显存、搬运、执行，角色≈CUDA Runtime）→CANN 算子库（取或现编译二进制）→Runtime→驱动/固件→AI Core。排查自底向上：驱动→CANN→torch-npu；「能 import、一跑就报错」正是下层缺失或版本不配套。注意 MindSpore 不走这条路：它由 CANN 图引擎 GE 编译、自有运行时 MindRT 调度，与 PyTorch 线平级。</details>

### 7. 算子融合为什么能提 decode 吞吐？这和算术强度是一件事吗？
<details><summary>查看答案</summary>是一件事的两面。融合让中间结果留在片上 UB（每核约 192 KB）不写回 HBM，省的是字节而不是 FLOP；算术强度＝FLOP÷字节，省了字节就等于抬高算术强度，让 decode 的 1 FLOP/字节更靠近平衡点 188，在带宽受限区间直接换成吞吐。反之若某算子已计算受限（大 batch 的 prefill），融合省带宽的收益就很小——这也解释了为什么第 8 课说融合对 vLLM 尤其重要：主力负载恰好是带宽受限的 decode。</details>

### 8. 「把 `--max-num-seqs` 拉到 64，吞吐一定更高」错在哪？抢占与 prefix caching 怎么互相救场？
<details><summary>查看答案</summary>错在忽略两道墙：显存上并发超出 KV 池后调度器频繁抢占，被抢占的请求释放块、回等待队列、重算 prefill，产生重复计算，有效吞吐反而降；延迟上场 batch 越大单步越慢，TPOT 恶化。救场关系：prefix caching 让被抢占的请求重算时可能直接命中前缀、恢复一部分进度；反过来，抢占造成的重算需求也让前缀缓存更值钱。默认策略 FCFS，可用 `--scheduling-policy priority` 按优先级抢占。</details>

## 易混淆对照表

| 容易混的概念 | 区别一句话 |
| --- | --- |
| prefill vs decode | 一次并行算完 prompt（计算受限）vs 每步只出一个 token（带宽受限）。 |
| TTFT vs TPOT vs 吞吐 | 首字体感（排队+prefill）／后续字间隔（decode 单步）／系统总产能。 |
| 计算受限 vs 带宽受限 | 看算术强度到没到「算力÷带宽」平衡点：89 ns 算 vs 28 µs 搬就是带宽受限。 |
| KV cache vs prefix caching | 自己的历史 K/V vs 跨请求按内容哈希复用相同前缀的块。 |
| continuous batching vs chunked prefill | 请求级随进随出 vs token 级把长 prompt 切块混批。 |
| `--max-num-seqs` vs `--max-num-batched-tokens` | 限同批请求数 vs 限每步 token 数，V1 以 token 预算为主。 |
| `--gpu-memory-utilization` vs KV 池 | 总配额（权重+激活+KV 共用）vs 扣完剩下的那块。 |
| AIC vs AIV | 带 Cube 的矩阵核 vs 向量核；初代 910 的 Vector 还在 AI Core 内。 |
| CANN vs AscendCL vs torch-npu | 整套底座 vs 暴露的 C 接口 vs 把 PyTorch 接上去的插件。 |
