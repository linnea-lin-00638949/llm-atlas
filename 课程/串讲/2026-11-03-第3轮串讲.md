# 第 3 轮串讲 · 2026-11-03

> 本轮四课：第 9 课 · 昇腾上的 vLLM：vllm-ascend 部署与调优（上）、第 10 课 · 昇腾上的 vLLM：vllm-ascend 部署与调优（下）、第 11 课 · 量化与编译基础、第 12 课 · 投机解码

## 一张图串起来

四课是同一本账的四个动作：**先算账、再测准、最后从三个位置把账砍下去**。

```text
              一个 token 的账（第 5–8 课留下的老账）
     一步耗时 ≈ (权重字节 + KV 字节) ÷ HBM 带宽      ← decode 天生带宽受限
                              │
     ┌────────────────────────┼─────────────────────────┐
  ①先能跑                  ②先测准                  ③再省字节/次数/摊薄
  第 9 课                  第 10 课                 第 11、12 课
  vllm-ascend              profiler 两步            量化    编译/融合   投机
  CANN→torch-npu→插件      算子级 vs 调度级         ÷2÷4   少往返      K+1 个
  版本矩阵整行锁           三步定位法              省带宽  省带宽      摊薄带宽
```

因果链这样读。

**① 能不能跑。** 原生 vLLM 没有昇腾后端，它不认识 `npu`、也不会为 NPU 编译 kernel——缺的不是加速包，而是**设备后端**；由 vllm-ascend 通过 entry point 注册进 `vllm.platform_plugins` 接管，压在 CANN 与 torch-npu 之上，三层版本必须整行锁。这一课顺手给出**第一个数**：Qwen3-0.6B 每 token KV 114,688 B（≈112 KiB），64 GB 卡 4096 上下文装 114 条，32768 只剩 14 条。

**② 是不是真在 NPU 上、快不快。** 能跑通不等于算子在昇腾上：fallback 有组合重写（一个拆成五个，仍在 NPU、正确但慢）和直接 `NotImplementedError`，torch-npu **不会**悄悄搬 CPU 替算。只能靠 profiler：算子级看 `kernel_details.csv`，服务级看 `batch.csv`。这一课把 decode 一步拆成四笔账——权重 16 GB÷1.6 TB/s = 10 ms、每 token KV 144 KB、算力 0.213 ms、通信 72×30 μs ≈ 2.2 ms——并给出**第二个数**：拐点 B\*≈47，只在 512 token 这种短上下文成立；8k 时 KV（38 GB）反超权重（16 GB），一步下界 34 ms，加并发就直接涨时间。

**③ 三个位置砍同一本账。** 第 11 课动**分子**：量化把字节减半（7B：14 → 7 → 3.5 GB），融合与编译省**往返**（少启动 kernel、中间张量留片上不写回 HBM），都在治访存浪费。第 12 课动**每次读取的产出**：K 个草稿接在前缀后，因果掩码让一次前向得出 K+1 组分布，一次读取服务最多 K+1 个 token，拒绝采样保证分布不变。

暗线：第 10 课的 B\* 与第 12 课的保本 `L > 1+K·c_d/c_t` 都是**平衡点**——一个问「加 batch 还赚不赚」，一个问「加草稿还赚不赚」，都不许背常数，要用实测效率项代进去重算。而第 11 课的量化减小 c_t，正好把投机的门槛抬高（见自测 4、5 题）。

## 综合自测

### 1. 64 GB 卡跑 Qwen3-8B（BF16）、`--max-model-len 4096`，KV 池多大、能装几条？为什么别把 `--gpu-memory-utilization` 拉到 1.0？
<details><summary>查看答案</summary>配额 64×0.9 = 57.6 GB，扣运行时与图捕获约 4 GB 得 53.6 GB；权重 8×10⁹×2 B = 16 GB，剩 37.6 GB。每 token 每层 KV = 2×8 头×128 维×2 B = 4 KB，36 层共 144 KB/token；一条 4096 token 请求约 0.56 GB，于是 37.6÷0.56 ≈ 66 条（KV 侧上界）。对照第 9 课 0.6B 的 114 条：模型大 13 倍，权重只多吃 15 GB，KV/token 却从 112 KiB 涨到 144 KB。拉到 1.0 会挤掉运行时、通信缓冲与图捕获的预留，典型是启动失败或运行中 OOM，0.8–0.9 是稳妥起点。</details>

### 2. B=32、512 token 上下文，实测每步 20 ms 而下界 11.5 ms。按什么顺序捞这 42%？若 `kernel_details.csv` 榜首是五个串联的逐元素小算子，说明什么？
<details><summary>查看答案</summary>先复算：(16+2.4)÷1.6 TB/s = 11.5 ms（32×144 KB×512 ≈ 2.4 GB KV），带宽利用率约 58%。归因三步：矩阵乘占比低 → 融合不足或回退；内核间空隙大 → 下发/调度，先试 `TASK_QUEUE_ENABLE=2`、`CPU_AFFINITY_CONF=1`；all-reduce 占比高 → 查 TP 与 HCCL。五个小算子串联正是**组合重写式 fallback**：每拆一次多一次 kernel 启动（几微秒）和一轮中间张量写回 HBM。这就是第 11 课说的融合收益——省的是字节而非 FLOP，中间结果留在片上就把带宽还回来。正确性从不报警，只有 profiler 报警。</details>

### 3. 同一个原生 FP8 checkpoint，为什么在 950PR 上显存减半、换张卡就「开了没变」？量化收益为何随上下文变长而衰减？
<details><summary>查看答案</summary>昇腾三条路：ModelSlim 产 W8A8 加 `--quantization ascend`；LLM-Compressor 产 compressed-tensors 格式；直接吃原生 FP8 checkpoint。只有**块级缩放且硬件是 950PR/950DT** 才真走 FP8 矩阵乘，其它代际把权重摊回 BF16 再算，显存按 BF16 规划。衰减看第 10 课的账：512 token 时 (8+2.4)÷1.6 = 6.5 ms 对 11.5 ms 约 1.8×；8k 时 (8+38)÷1.6 = 29 ms 对 34 ms 只有 1.2×。量化压的是权重，**KV 一字节没省**，上下文越长 KV 占比越高。第 9 课的 114,688 B/token 就是量化动不了的那一半。</details>

### 4. c_t=30 ms、c_d=3 ms、K=4、α=0.7 时加速 1.98×。若先做 weight-only INT8 把 c_t 压到 15 ms、草稿几乎没变，收益变成多少？
<details><summary>查看答案</summary>原配置 L = 1+0.7+0.49+0.343+0.2401 = 2.7731，一轮 12+30 = 42 ms，15.1 ms/token，1.98×。量化后保本门槛 L > 1+K·c_d/c_t = 1+4×3/15 = 1.8，实际 2.77 仍高于门槛，还赚；但一轮 12+15 = 27 ms，27÷2.7731 ≈ 9.7 ms/token，相对 15 ms 只有 **1.54×**（相对原始 30 ms 是 3.1×）。结论：两个优化**不同乘**。量化只压 c_t 不压 c_d，`c_d/c_t` 从 0.1 恶化到 0.2，门槛从 1.4 抬到 1.8，K 也该跟着调小：K=2 时 L=2.19、一轮 21 ms、9.6 ms/token，几乎持平但少花草稿算力。参数不是独立旋钮。</details>

### 5. 第 10 课算出 TP=4 把 decode 从 10 ms 压到 4.7 ms。此时叠加投机解码（c_d=3、K=4、α=0.7）划算吗？
<details><summary>查看答案</summary>不划算，甚至更慢。门槛变成 L > 1+4×3/4.7 ≈ 3.55，而 α=0.7 只有 2.77；一轮 12+4.7 = 16.7 ms，16.7÷2.7731 ≈ 6.0 ms/token，比不投机的 4.7 ms 更慢。要让 K=4 保本，α 得爬到约 0.83（α=0.85 时 L≈3.71）。机制是两者砍**同一笔权重读取**：TP 靠切分把每卡读取摊薄 4 倍，投机靠 K+1 个位置摊薄同一次读取，叠加时省下的空间被重复占用，2.2 ms 通信固定延迟却一分不少。真要叠加就选 c_d 极小的方案（n-gram 近乎零成本、EAGLE 薄头），而不是独立 draft model。</details>

### 6. 五个现象各落三层栈哪一层、下一步查什么：① `npu-smi` 看不到卡；② `torch.npu.is_available()` 为 False；③ 日志没有 `Platform plugin ascend is activated`；④ `import torch_npu` 抛错；⑤ 服务起来却报 CUDA 错误。
<details><summary>查看答案</summary>① 驱动/固件或容器映射，查 `--device /dev/davinci0`，别急装 Python 包；② CANN 或 torch-npu 版本段，`pip list` 对矩阵；③ 插件没接管，查 vllm-ascend 与 vLLM 版本；④ torch 与 torch_npu 的 ABI 不匹配，通常在 import 或首个 npu 算子处报「找不到符号」，修法是换整行；⑤ 仍是插件没加载，vLLM 在按 CUDA 找设备。规律：**报错位置常离真正原因很远**，三层各有独立的存在性检查，永远自底向上查。第 10 课补一点：`vllm_ascend/patch` 会在 import 时替换少数函数，「参数不按文档生效」可能出自补丁层。</details>

### 7. 线上 Qwen3-8B、8k 上下文、TP=4，TPOT 55 ms。按什么顺序动旋钮，每步预期与代价是什么？
<details><summary>查看答案</summary>先算账：8k 时每卡 (4+9.5)÷1.6 ≈ 8.4 ms，加通信约 10.6 ms，即应在 10 ms 量级；55 ms 意味着 5 倍水分，先别调参、先 profile。① 归因：矩阵乘占比低 → 回退/融合不足；空隙大 → 下发，试 `TASK_QUEUE_ENABLE=2`、`CPU_AFFINITY_CONF=1`；all-reduce 占比高 → 查 HCCL 与 TP 拓扑。② 若是算子问题走 W8A8（ModelSlim + `--quantization ascend`），预期权重读取减半、8k 下约 1.2×，代价是精度与量化后端必须验；别指望 FP8 checkpoint 在非 950PR 上省显存。③ 若是组批问题看 `batch.csv`，batch 长期起不来是并发预算问题，与量化无关。④ 投机放最后：TP 已把 c_t 压到 4.7 ms，独立 draft model 基本必亏（见第 5 题），只有 n-gram 或极薄的头可能保本。顺序即 **profiler → 融合/下发 → 量化 → 并行与投机，每步重算门槛，不套模板**。</details>

## 易混淆对照表

| 容易混的概念 | 区别一句话 |
| --- | --- |
| vLLM vs vllm-ascend | 引擎本体（API、调度、PagedAttention 全原装）vs 只替换「跟硬件打交道那层」的插件。 |
| CANN vs torch-npu vs vllm-ascend | 运行时+算子库+通信库 vs PyTorch 的 `npu` 后端 vs 用这套后端写出来的插件。 |
| 组合重写 vs `NotImplementedError` | 一个算子拆成五个、仍在 NPU 上跑（正确但慢）vs 直接报错；**都不会自动搬 CPU**。 |
| B\*≈47 vs 投机保本 L\* | 「算力下界追上带宽下界」的 batch vs 「一轮成本追平单步成本」的接受长度。 |
| 条件接受率 αᵢ vs 聚合接受率 | 「前 i−1 个都过了之后第 i 个通过」（α=0.7 连过 4 个只有 24%）vs 监控的 accepted/drafted（本例约 44%）。 |
| L（接受长度）vs 加速比 | L=1+Σαⁱ 是一轮产出几个 token vs 加速比还要除上草稿成本。 |
| W8A8 vs W4A16 | 权重激活都 8 位、要 SmoothQuant 搬激活离群值 vs 只压权重、激活仍 FP16，配 AWQ/GPTQ 与分组。 |
| 量化省显存 vs 一定变快 | 省显存基本确定；变快只在带宽受限区间成立，prefill 或大 batch 时 INT4 现场反量化可能更慢。 |
| FP8 checkpoint vs ModelSlim W8A8 | 前者要块级缩放且 950PR/950DT 才真走 FP8，否则摊回 BF16 vs 后者是明确的量化后端。 |
| 量化 vs 编译 | 少用字节（省带宽）vs 少往返次数（省启动与 HBM 写回），都治访存浪费。 |
| PTQ vs QAT | 几百条样本跑前向、分钟到小时 vs 插伪量化节点加 STE 训练、小时到天；W4A4 只能靠后者。 |
| `--max-model-len` 大 vs 启动失败 | 只有单条 max-model-len 的 KV 装不进池子才报错；小模型上表现为并发骤降（114→14）。 |
| TTFT 差 vs TPOT 差 | 前者查排队与 prefill（prefix caching、chunked prefill）vs 后者查 decode 单步（权重量化、融合、TP、投机）。 |
