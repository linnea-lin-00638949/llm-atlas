# 第 14 课 · 推理成本与调度

> 学完今天，你能：
> 1. 把推理成本拆成「单价 ÷ SLO 下的有效吞吐 ÷ 利用率」三个可算因子；
> 2. 把 TTFT、TPOT 换算成并发上限与 batch，用来定调度、扩缩容与拒绝策略；
> 3. 用自己业务的流量、机器价格与利用率，算出 $/token 与报价毛利。

## 课前自测

1. 8 卡服务器 32 元/小时，SLO 下满载输出 1,500 token/s。每百万输出 token 多少钱？利用率 60% 时呢？
2. 「加速卡利用率 90%」能说明省钱吗？它等于成本公式里的利用率吗？
3. 输入 500 / 输出 200 的请求，成本主要落在哪一半？换成 8,000 / 100 呢？
4. TPOT ≤ 50 毫秒、整机 1,500 token/s，最多跑多少路解码？怎样用它校验 `--max-num-seqs`？

## 为什么需要它

回顾前置：serving-basics 把生成分成 prefill（预填充，一次算完整段输入的 KV）与 decode（解码，逐 token 吐出）；连续批处理（按迭代调度）与分页 KV cache（PagedAttention）让显存被多请求共享。pd-disagg 把两阶段拆到不同实例、用 KV 传输衔接。KV 即 Key-Value 缓存。

这些答的是「怎么快」。工程上还要答「多快才够、花多少钱」：卡按小时计费，空转也烧钱；延迟随负载恶化，批塞满就违约；业务方要报价，你得说得出单位成本。三者把承诺、调度与成本绑成链。

## 核心概念

### SLO（服务等级目标）

定义：SLO 是对服务质量的可度量承诺，如「99% 的请求首 token 延迟低于 2 秒」。度量它的实测值叫 SLI（Service Level Indicator），如 P99 首 token 延迟——排序后第 99% 位置的值，1% 请求更慢。

直觉：SLO 是预算，不是越高越好。P99 从 2 秒收紧到 1 秒，往往多备一倍机器。

机制：调度器把 SLO 翻成准入条件——最大并发、最大批大小（batch，一次迭代同时处理的请求数）、排队上限、超时拒绝。关键在「敢拒绝」：过载时明确失败，而不是一起变慢。两个最常用的 SLI：TTFT（Time To First Token，首 token 延迟，由排队加 prefill 决定）与 TPOT（Time Per Output Token，输出间隔，由 decode 决定）——它们能反推容量，见第 2 步。

### autoscaling（自动扩缩容）

定义：按负载增减副本数。Kubernetes 的标准组件是 HPA（Horizontal Pod Autoscaler，水平 Pod 自动扩缩容），按比例调：期望副本 ≈ 向上取整(当前副本 × 当前指标 ÷ 目标指标)。

直觉：餐厅加桌子。但 LLM 的桌子要先把几十 GB 权重搬进显存，再做图捕获（graph capture，把一步计算录成可重放的图）、跑预热，冷启动常见几十秒到几分钟。

机制：扩容用领先指标（排队数、TTFT），别用 CPU——算力在 NPU（Neural Processing Unit，神经网络处理器）上，CPU 基本闲着；缩容要慢，连续多周期低于阈值才减；护栏：最小副本保 SLO，最大副本防账单爆炸。昇腾上单卡显存切分在启动时定死，扩缩容粒度是整卡或整机。

### 多租户

定义：一套服务同时服务多个客户，彼此逻辑隔离。

直觉：合租公寓——省房租，但有人半夜开派对全屋都听得到。

机制：四件事——配额（每租户并发与 token 速率上限）、优先级（不同 SLO 分开排队）、公平调度（防 noisy neighbor，即某租户的大请求占满共享资源）、数据隔离（前缀缓存必须按租户隔离，否则 A 的私有提示词可能被 B 命中复用）。代价：分区共享降低利用率、抬高 $/token（单位 token 成本）——本课最重要的权衡。

### 缓存

定义：复用已算过的中间结果。LLM 服务里主要是前缀缓存（prefix caching）：相同开头（固定系统提示词、固定示例）的 KV 块按内容哈希建索引，命中就跳过 prefill。

直觉：餐馆提前熬好的高汤，来了就盛。

机制：按 token 块哈希，命中即复用显存里的 KV；需要淘汰策略（常用 LRU，Least Recently Used）与租户隔离。代价：缓存占显存、挤压并发；且只省 prefill。值多少钱取决于输入输出结构，见第 5 步。

### $/token

定义：单位 token 成本，按百万 token 计。一条式子把单位写全：

每百万 token 成本 = 每小时机器成本 ÷ (每小时有效 token 数 ÷ 10^6) ÷ 利用率

**利用率**必须先定义：利用率 = 计费时间里满足 SLO 的有效产出 ÷ 满载产出，含低谷闲置与为扛峰值的冗余，是「成本利用率」，不是 NPU 占用率。卡 90% 时间在算，但若 batch 小或在跑超 SLO 流量，成本利用率可能只有 50%，两者不能混用（见误区一）。

「有效」是灵魂：只有满足 SLO 的吞吐才进分母。校验：32 元/小时、满载 1,500 token/s，32 ÷ 5.4 ≈ 5.93 元/百万（利用率 1）；利用率 0.6 时 5.93 ÷ 0.6 ≈ 9.88 元/百万。两个数都对，差的只是口径——别扣两次。

直觉：分子是你付的钱，分母是你真正卖出去的产出。

机制：三个因子——单价（卡型、精度、量化）、吞吐（batch、并行、缓存）、利用率（负载曲线与冗余）；为扛峰值多备的机器，低谷就是纯浪费。

### 定价

定义：对外报价规则。两条路线：成本加成（按目标毛利率加价）与按价值（客户愿为省下的人力付多少）。

机制：成本加成必须写毛利率口径，否则手算复现不出来：

报价 = 满载单请求成本 ÷ 目标利用率 ÷ (1 − 目标毛利率)

本例 0.00193 ÷ 0.6 ÷ 0.72 ≈ 0.00447 元，回算毛利率 28.4%。别写成「成本 × (1 + 毛利率)」——那是加价率（markup）：28% 的加价率只对应 21.8% 的毛利率，差 8 个点。

价格表还要落：输入输出分开计价、缓存命中打折、离线批处理打折（用空闲算力）、预留容量比按需便宜（买方替卖方承担空转风险）。价格公开后难改，先用成本模型算地板价。

## 一步一步理解

场景：一台 8 卡昇腾 910B，按需 32 元/小时（假设价，换成你的采购价），模型约 7B。压测在「P99 TTFT ≤ 2 秒、TPOT ≤ 50 毫秒」下得到两组数：输出 1,500 token/s、prefill 6,000 输入 token/s，分别压测、不可叠加。流量：平均输入 500、输出 200 token。

- 第 1 步 每秒成本：32 ÷ 3600 = 0.00889 元/秒。
- 第 2 步 把 SLO 换成并发上限。TPOT ≤ 50 ms ⇒ 每路每秒 20 token ⇒ 1,500 ÷ 20 = 75 路，这就是 `--max-num-seqs` 的校验值。TTFT 的 2 秒里，500 token 的 prefill 按 6,000 tok/s 只花约 0.08 秒，剩下约 1.9 秒是排队预算。显存侧：32 层、32 头 × 128 维、fp16 下每 token 的 KV 约 512 KB，单请求 700 token ≈ 350 MB，75 路约 26 GB，8 卡 TP 后每卡 3.3 GB——不卡显存，卡带宽（TPOT）。
- 第 3 步 每小时输出 1,500 × 3600 = 5.4 百万 token；输出侧满载成本 32 ÷ 5.4 = 5.93 元/百万，按 1 美元 ≈ 7.2 元人民币约 $0.82。
- 第 4 步 输入侧满载成本：6,000 × 3600 = 21.6 百万/小时，32 ÷ 21.6 = 1.48 元/百万输入 token。
- 第 5 步 贵几倍是算出来的：成本比 = 输入吞吐 ÷ 输出吞吐 = 6,000 ÷ 1,500 = 4，即输出单价是输入的 4 倍。输出是否占主体看 token 数之比：本例输入/输出 = 2.5 < 4，输出占 62%；RAG 的 8,000 / 100 = 80 > 4，输入 0.01184 元占 95%，prefill 才是主体。若 prefill 实测 20,000 tok/s，输入只要 0.44 元/百万，输出就是 13 倍。
- 第 6 步 单请求成本：500 × 1.48/10^6 + 200 × 5.93/10^6 = 0.00074 + 0.00119 = 0.00193 元。口径：两组吞吐分别压测，按「机器时间可加」折算——500 ÷ 6,000 = 0.083 s 加 200 ÷ 1,500 = 0.133 s，共 0.217 s，× 0.00889 = 0.00193 元。真实混合流量会因 chunked prefill 开销、KV 抢带宽更慢（PD 分离的理由），故 0.00193 是下限；做过混合压测就直接用混合吞吐。
- 第 7 步 加利用率：日均 60%，0.00193 ÷ 0.6 = 0.00322 元/请求，等价 9.88 元/百万输出 token。
- 第 8 步 定价与毛利：报价 3 元/百万输入、15 元/百万输出。单请求收入 = 500 × 3/10^6 + 200 × 15/10^6 = 0.0045 元。毛利率 = (0.0045 − 0.00322) ÷ 0.0045 ≈ 28%。
- 第 9 步 压力测试，两个变量分开看：

| 情形 | 有效吞吐 | 利用率 | 单请求成本 | 毛利率 |
| --- | --- | --- | --- | --- |
| 基准 | 1,500 tok/s | 60% | 0.00322 元 | +28% |
| 促销低谷 | 1,500 tok/s | 30% | 0.00643 元 | −43% |
| 只提吞吐、低谷不变 | 2,000 tok/s | 30% | 0.00543 元 | −21% |
| 提吞吐 + 恢复 60% | 2,000 tok/s | 60% | 0.00271 元 | +40% |

最后一行：单请求成本 (0.00074 + 0.000889) ÷ 0.6 = 0.002715 元，毛利 39.7%；吞吐 2,000 意味着按 TPOT 50 ms 能跑 100 路，`--max-num-seqs` 要重测。

结论：赚不赚钱取决于有效吞吐、利用率、SLO 有没有被偷偷突破——三件事都归调度管。顺序：先定 SLO，再按第 2 步换成并发与 batch，最后谈扩缩容与定价。

落到昇腾的三个旋钮（vLLM，开源推理引擎）：`--max-model-len` 限单请求上下文，`--max-num-seqs` 限同时在跑的序列数（校验值 75 路），`--gpu-memory-utilization` 决定 KV cache 占多少显存。三者共同决定分母。扩缩容时 HPA 接 `vllm:num_requests_waiting`（排队数）或 `vllm:time_to_first_token_seconds` 分位数，别接 CPU；指标名以官方 Production Metrics 文档为准。

## 常见误区

误区一：利用率越高越省钱。先问哪种利用率：卡忙不等于卖出产出，batch 小或跑超 SLO 流量时占用率高、有效产出低。decode 受带宽限制，batch 拉大 TPOT 变长，超 50 毫秒的多余吞吐是「违约吞吐」——拿它算成本等于用超速的油耗算省油。

误区二：自动扩缩容能解决成本。LLM 扩容是分钟级的（加载权重 + 图捕获 + 预热），追不上秒级尖峰；卡按小时计费，缩容不等于退钱。降价靠提高单位卡有效吞吐（量化、前缀缓存、连续批处理、PD 分离），扩缩容主要保 SLO。

误区三：缓存命中率高就等于便宜。前缀缓存只省 prefill：8,000 / 100 的 RAG 里它是主角，500/200 的短对话里输出占 62%，救不了多少。更隐蔽的是缓存占显存、挤掉并发，可能让输出吞吐下降、$/token 反升。要同时看命中率与 kv_cache_usage_perc（KV 占用比例）。

误区四：SLO 定得越严越专业。SLO 是花钱的开关：客服能忍 3 秒，语音助手忍不了 800 毫秒；P99 定在真实忍耐线附近，钱才花对。

## 一句话总结

每百万 token 成本 = 每小时成本 ÷ (每小时有效 token 数 ÷ 10^6) ÷ 利用率。代入本课数据：32 ÷ 5.4 ÷ 0.6 ≈ 9.88 元。SLO 压住分母上限，调度决定你贴近多少，定价决定你赚不赚。

## 自测题

### 1. 满载 1,500 token/s、32 元/小时，每百万输出 token 多少钱？要 28% 毛利该报多少？
<details><summary>查看答案</summary>满载：32 ÷ (1,500 × 3600 ÷ 10^6) = 32 ÷ 5.4 ≈ 5.93 元/百万，按 1 美元 ≈ 7.2 元约 $0.82；含 60% 利用率：5.93 ÷ 0.6 ≈ 9.88 元/百万（扣两次得 16.5 元是错的）。报价按毛利率口径：0.00193 ÷ 0.6 ÷ (1 − 0.28) ≈ 0.00447 元/请求；写成 0.00322 × 1.28 是加价率口径，毛利只有 21.8%。回指「$/token」「定价」与第 3、7、8 步。</details>

### 2. 同事说「卡利用率 90%，我们很省钱」，怎么反驳？
<details><summary>查看答案</summary>卡忙不省钱，卖出满足 SLO 的 token 才省钱。NPU 占用率 90% 可能来自小 batch 或超 SLO 流量，成本利用率也许只有 50%——此时每百万成本是 5.93 ÷ 0.5 ≈ 11.9 元，而非 5.93 ÷ 0.9 ≈ 6.6 元，照着报价会亏。回指「$/token」的利用率定义与误区一。</details>

### 3. 输入 500 / 输出 200 与 8,000 / 100，成本结构差在哪？
<details><summary>查看答案</summary>成本比 = 6,000 ÷ 1,500 = 4。前者输入/输出 = 2.5 < 4，输出占 62%（0.00119 / 0.00193）；后者输入/输出 = 80 > 4，输入 0.01184 元、输出 0.000593 元，输入占 95%。所以短输入优化 decode（batch、量化、投机解码），长输入 RAG 优化 prefill（前缀缓存、chunked prefill、PD 分离）。回指第 5 步与误区三。</details>

### 4. TPOT ≤ 50 ms、整机 1,500 token/s，能跑多少路解码？TTFT 的 2 秒怎么分？
<details><summary>查看答案</summary>TPOT 50 ms ⇒ 每路 20 token/s ⇒ 1,500 ÷ 20 = 75 路，作为 `--max-num-seqs` 的校验值。2 秒里 prefill 500 token 约 0.08 秒，其余约 1.9 秒是排队预算；预算吃满就加副本、按租户限流或拒绝。75 路约 26 GB KV，显存不是瓶颈——先调 batch 与 TPOT，再谈加卡。回指第 2 步。</details>

## 术语卡

| 术语 | 解释 |
| --- | --- |
| SLO | 可度量的质量承诺，如「99% 请求 TTFT < 2 秒」。 |
| SLI | 度量 SLO 的实测值，如 P99 首 token 延迟。 |
| TTFT | 首 token 延迟，由排队与 prefill 决定。 |
| TPOT | 输出 token 间隔，由 decode 决定；50 ms 即每路 20 token/s。 |
| autoscaling | 按负载自动增减副本。 |
| HPA | Kubernetes 的水平自动扩缩容组件，按指标比例调副本。 |
| 多租户 | 一套服务服务多客户，靠配额、优先级、公平调度、数据隔离区分。 |
| 前缀缓存 | 复用相同开头的 KV 块，只省 prefill。 |
| 有效吞吐 | 满足 SLO 的吞吐，是分母里唯一算数的部分。 |
| 利用率 | 计费时间内满足 SLO 的有效产出 ÷ 满载产出；≠ NPU 占用率。 |
| 冷启动 | 新副本从启动到能服务的时间，含加载权重、图捕获、预热。 |
| $/token | 按百万 token 计：每小时成本 ÷ (每小时有效 token 数 ÷ 10^6) ÷ 利用率。 |
| 成本加成定价 | 报价 = 成本 ÷ 目标利用率 ÷ (1 − 目标毛利率)；×(1 + 毛利) 是加价率口径。 |
