# 第 6 课 · vLLM 引擎架构

> 学完今天，你能：

> 2. 解释 prefix caching 为什么能省 prefill
> 3. 说清调度器在权衡什么（延迟 vs 吞吐），读懂启动参数里的关键项

## 课前自测
1. 为什么 vLLM 要把 KV cache 切成 16 token 一块的「页」，而不是给每个请求整段预留？
2. 100 个请求共享同一段 1000 token 的系统提示词，prefix caching 大约省掉多少次 prefill？
3. 把 `--max-num-seqs` 调大，吞吐一定变高吗？

## 为什么需要它
先回顾 serving-basics：LLM 推理分两个阶段——prefill（预填充，一次性算完整个 prompt）和 decode（解码，每步生成一个 token）；延迟指单个请求的响应耗时，吞吐指单位时间处理的请求或 token 数。朴素做法「一个请求跑完再接下一个」有两个问题：一是显存浪费——为最长序列预留一整段连续 KV cache，大部分时间闲置；二是设备空转——decode 每步只算一个 token，计算量小，单请求占不满 NPU（神经网络处理器，昇腾的加速芯片）。vLLM 是业界主流开源推理引擎，用「页式内存池 + token 预算调度 + 前缀缓存」把一张卡塞进成百上千个并发请求。学完本课，你能画出主链路、手算 KV 显存账、读得懂启动参数。本课只讲架构地基，不追版本新闻。

## 核心概念
### vLLM V1
定义：vLLM 当前默认的引擎架构，2025 年发布 alpha 版，官方现已废弃旧版 V0。V1 保留 V0 的模型实现与算子（矩阵乘等底层计算单元），重写了调度器、KV 缓存管理、worker 和 API 服务。
直觉：老房子功能越堆越多、管道互相缠绕；V1 是拆掉内墙重排后的统一布局。
机制：多进程架构——API Server 进程（HTTP 与分词）、Engine Core 进程（调度与 KV 管理）、每个 NPU 一个 Worker 进程（加载权重、执行前向计算），进程间用 ZMQ（跨进程消息队列）通信。

### Engine Core（引擎核心）
定义：运行调度器、管理 KV 缓存、协调设备 worker 执行模型计算的核心进程。
直觉：餐厅前台经理——接单、排菜、通知后厨，全程不碰锅。
机制：一个忙碌循环（busy loop），每个 step 调度一次、向 NPU worker 派发一次；请求的排队、运行、抢占、完成等状态都在这里维护。注意：采样不在这里做——它只汇总 worker 返回的采样结果并更新状态。

### scheduler（调度器）
定义：决定「这一步让哪些请求、算多少个 token」的组件。V1 采用 token 预算制：每步把 `--max-num-batched-tokens` 个 token 的预算，分配给等待中和运行中的请求。
直觉：高速公路入口限量放行——每步只放总量不超预算的车。
机制：没有严格的 prefill/decode 两个阶段（那是 V0 的设计）；每个请求记录「已算到第几个 token」，调度器给它补 token，长 prompt 因此被切块计算（chunked prefill）。当 KV 缓存不足时发生抢占（preemption）：按策略挑运行中的请求，释放它的 KV 块、踢回等待队列，重新准入时重算。默认策略 FCFS（First-Come-First-Served，先来先服务），也可用 `--scheduling-policy priority` 按请求优先级抢占。被抢占的请求重算 prefill 时，前缀缓存还可能帮它直接恢复一部分进度。这就是延迟与吞吐的权衡：一步塞得越多，吞吐越高，但单步耗时变长、单请求延迟上升，KV 也更紧张。

### 内存池（KV cache / PagedAttention）
先回顾：KV cache 是每层注意力算出的 K、V 向量缓存，decode 时靠它避免重算历史 token。
定义：vLLM 把 KV 缓存切成固定大小的块（block，默认 16 token/块），像操作系统内存分页一样按需分配：逻辑上连续，物理上不必连续。
直觉：整段预留像给每个旅行团包下一整层酒店，旺季必浪费；分页像散客按房间入住，退房即回收。
机制：每个请求维护一张「块表」记录它的 KV 块编号；注意力 kernel 按块表寻址取数（PagedAttention，出自 vLLM 团队的 SOSP 2023 论文，SOSP 指操作系统领域顶级学术会议）。碎片几乎为零，是支持大量并发请求的地基；论文实测传统整段预留方案显存浪费可达 60%–80%，分页方案压到 4% 以下。

### prefix caching（前缀缓存）
定义：把算完的 KV 块按内容做哈希（把任意内容压成固定长度的指纹，便于快速比对）缓存；新请求的 prompt 与历史请求共享前缀时直接复用这些块，跳过那部分 prefill。
直觉：两封邮件开头是同一段公司介绍——打字机时代要重打，电脑时代复制粘贴一次即可。
机制：只缓存完整块；块的哈希 = 父块哈希 + 块内 token ID（多模态输入再拼图像哈希），默认 SHA-256（自 v0.10.2 起），碰撞概率可忽略。命中后只省 prefill 计算与 KV 内存，不省 decode。典型场景：反复查询同一长文档、多轮对话共享历史。

### OpenAI 兼容 API
定义：`vllm serve <模型>` 启动的 HTTP 服务，实现 OpenAI 的接口协议（`/v1/chat/completions`、`/v1/completions`、`/v1/models`）。
直觉：标准化插座——上层应用把 base_url 指过来就能用，无需改调用代码。
机制：API Server 进程用 FastAPI（Python Web 框架）实现，负责分词、把请求转成引擎内部格式，经 ZMQ 交给 Engine Core。

## 一步一步理解
主链路（建议画出来）：HTTP 请求 → API Server 分词 → ZMQ → Engine Core 调度 → NPU Worker 前向计算并采样（按概率分布从词表挑出下一个 token）出 1 个 token → Engine Core 汇总结果、更新调度状态 → API Server 流式返回。每生成一个 token 都回到调度器再走一轮，直到命中结束符或达到 max_tokens（最大生成长度）。

手算例子（跟着算。模型取 Llama-2 7B：32 层、32 个 KV 头、每头 128 维、FP16 每个数 2 字节）：
第 1 步：每个 token 每层 KV = 2（K、V 各一份）× 32 头 × 128 维 × 2 B = 16,384 B = 16 KB。
第 2 步：每个 token 全模型 KV = 16 KB × 32 层 = 512 KB。
第 3 步：一个 2048 token 的请求约占 512 KB × 2048 ≈ 1 GB。64 GB 显存的 NPU，减掉权重约 14 GB（7B × 2 B），最多同时装约 (64−14)÷1 = 50 个这样的请求——这就是内存池为何要精打细算。注意：这是忽略激活值等临时显存占用的粗算上界，实际并发数会更低，把 50 当量级、别当容量。
第 4 步：prefix caching 的账。prefill 计算量估算公式 2·N·P（N 为参数数、P 为 prompt 长度，单位 FLOPs，即浮点运算次数）：2 × 7×10⁹ × 1000 ≈ 1.4×10¹³。对照：decode 每 token 约 2·N ≈ 1.4×10¹⁰，算一遍 1000 token 的 prefill 相当于 1000 次 decode 的算力。100 个请求共享同一段 1000 token 系统提示词时，不开缓存要算 100 次，开缓存只算 1 次，省 99 × 1.4×10¹³ ≈ 1.4×10¹⁵ FLOPs；按有效算力 100 TFLOPS 估算约省 14 秒纯计算（量级参考，不含访存等开销）。

昇腾落地：装好 vllm-ascend 插件后，启动日志出现 `Platform plugin ascend is activated` 即已接管 NPU 后端；内网拉模型可设 `export VLLM_USE_MODELSCOPE=True`。示例启动命令：
`vllm serve Qwen/Qwen3-8B --tensor-parallel-size 4 --max-model-len 8192 --max-num-batched-tokens 16384 --gpu-memory-utilization 0.9 --enable-prefix-caching`
逐项读：`--tensor-parallel-size 4` 把权重切到 4 张 NPU；`--max-model-len 8192` 限制最长上下文（决定 KV 池上限）；`--max-num-batched-tokens 16384` 每步 token 预算；`--gpu-memory-utilization 0.9` 允许用 90% 显存（余下留给 KV 池）；`--enable-prefix-caching` 开前缀缓存（新版默认已开启，显式传入无妨；用 `--no-enable-prefix-caching` 可关闭）。CANN（Compute Architecture for Neural Networks，昇腾异构计算架构，下一课展开）与 TorchNPU（PyTorch 的昇腾后端）的依赖版本以所用 vllm-ascend 版本的官方文档为准，写作时稳定版 v0.23.0 对应 CANN 9.1.0。

## 常见误区
1. 「prefix caching 让生成也变快」。错：它只省 prefill 计算，decode 逐 token 生成不受影响。回答越长、共享前缀越短，收益越小。
2. 「并发（max_num_seqs）越大吞吐越高」。错：并发超出 KV 容量后调度器频繁抢占，被抢占的请求释放缓存、重新排队、重新 prefill，产生重复计算；batch 越大单步越慢，延迟也恶化。吞吐和延迟必须一起看。
3. 「V1 有独立的 prefill 队列和 decode 队列」。错：V0 把 prefill 和 decode 分阶段分批调度、互不混批；V1 统一 token 预算，长 prompt 切成块（chunked prefill），与 decode 同批执行。

## 一句话总结
vLLM 用页式 KV 内存池、token 预算调度和前缀缓存把设备算力与显存吃满，在延迟与吞吐之间做显式权衡，再以 OpenAI 兼容 API 对外服务。

## 自测题
### 1. 为什么 vLLM 要把 KV cache 切成 16 token 一块的「页」？
<details><summary>查看答案</summary>整段预留按最长序列分配连续显存，大部分时间闲置，浪费可达 60%–80%；分页按需分配、逻辑连续物理不必连续，注意力 kernel 按块表寻址取数（PagedAttention），碎片几乎为零（4% 以下），是支撑大并发的地基。</details>

### 2. 100 个请求共享同一段 1000 token 系统提示词，prefix caching 大约省掉多少次 prefill？
<details><summary>查看答案</summary>约 99 次：第一个请求照常计算并把 KV 块写入缓存，其余 99 个命中同一前缀、直接复用 KV 块，跳过那 1000 token 的 prefill。注意只省 prefill 计算与 KV 内存，decode 逐 token 生成照常进行。</details>

### 3. 把 `--max-num-seqs` 调大，吞吐一定变高吗？
<details><summary>查看答案</summary>不一定。并发超出 KV 容量后调度器频繁抢占：被抢占请求释放 KV 块、重新排队、重新 prefill，产生重复计算；batch 变大单步耗时也变长，延迟恶化。吞吐必须和延迟一起看。</details>

### 4. Llama-2 7B（32 层、32 个 KV 头、每头 128 维、FP16）一个 2048 token 的请求约占多少 KV 显存？
<details><summary>查看答案</summary>每 token 每层 KV = 2×32×128×2 B = 16 KB；全模型 = 16 KB×32 层 = 512 KB/token；2048 token ≈ 1 GB。64 GB 卡减权重约 14 GB 后 (64−14)÷1 ≈ 50 个——这是忽略激活值等临时显存的粗算上界，实际并发更低。</details>

### 5. 主链路里「采样出 1 个 token」发生在哪个进程？
<details><summary>查看答案</summary>在 NPU Worker：V1 把 sampler 放进 model runner，随前向计算在设备端完成采样（按概率分布从词表挑下一个 token）。Engine Core 只接收采样结果、汇总并更新调度状态，自己不执行采样。</details>

## 术语卡
| 术语 | 解释 |
| --- | --- |
| prefill | 预填充：一次性计算整个 prompt，产生第一个新 token |
| decode | 解码：每次用已有 KV cache 生成一个 token，直到结束符 |
| KV cache | 每层注意力的 K、V 向量缓存，避免重复计算历史 token |
| block | KV 缓存的最小分配单位（默认 16 token/块），类似内存分页 |
| PagedAttention | vLLM 论文（SOSP 2023）提出的按块表寻址的注意力计算 |
| chunked prefill | 把长 prompt 切成块分批 prefill，避免独占设备 |
| token 预算 | 每步最多处理的 token 数（--max-num-batched-tokens） |
| 抢占（preemption） | KV 不足时强制部分请求释放缓存、重新排队 |
| FCFS | First-Come-First-Served，先来先服务，默认调度策略 |
| prefix caching | 按内容哈希复用已算 KV 块，跳过共享前缀的 prefill |
| 采样（sampling） | 按概率分布从词表挑出下一个 token，V1 中在 Worker 设备端完成 |
| 哈希（hash） | 把任意内容压成固定长度指纹，便于快速比对 |
| Engine Core | 运行调度器、管理 KV 缓存、协调 worker 的核心进程 |
| vllm-ascend | 让 vLLM 运行在昇腾 NPU 上的官方社区插件 |
